### TeamFlow / 企画書


### 第1章 事業概要

#### 1.1 背景・市場

中小〜中堅企業ではタスク・プロジェクト管理がスプレッドシートやチャットに分散し、進捗の可視化不足・属人化・情報の分断が起きている。クラウドで手軽に導入でき、月額サブスクで使えるBtoB SaaSの需要が拡大している。


#### 1.2 目的・ビジョン

- チームのタスク・進捗を1画面で可視化するSaaSを提供する
- マルチテナントで即日利用開始でき、プランに応じて拡張できる
- MRR(月次経常収益)の継続成長とChurn(解約率)低減を実現する


#### 1.3 提供価値（バリュープロポジション）

「登録から5分で使い始められ、チームの状況がひと目で分かる」。導入・運用の手間を最小化し、管理者は進捗を、メンバーは自分のタスクを迷わず把握できる。

### 第3章 プロダクト方針(MVP)

#### 3.1 基本方針

- MVPは『テナント登録→プロジェクト→タスク→通知→ダッシュボード』に集中
- マルチテナントSaaSとしてクラウドネイティブに構築
- 課金はStripe連携でサブスク化、Freeからの転換を狙う


#### 3.2 プロダクトコンセプト

ステートレスなWebアプリ＋共有DB（tenant_idで論理分離）で構成。SSO・公開API・Webhookでエコシステム連携を可能にし、プラン（Free/Pro/Business）で機能と上限を制御する。

### TeamFlow / SEO・公開ページ設計


### 第1章 方針・対象

> ※ 対象は公開ページ。アプリ本体(認証後)はnoindexで検索対象外とする。

| 対象 | SEO | 方針 |
| --- | --- | --- |
| LP/料金/機能紹介 | 対象 | SSR/SSGでインデックス最適化 |
| ブログ/導入事例 | 対象 | コンテンツSEO |
| ヘルプ/FAQ | 対象 | 構造化データ(FAQ) |
| 公開共有ページ | 対象(一部) | noindex切替可 |
| アプリ(認証後) | 対象外 | noindex/robotsで除外 |

### 第2章 レンダリング方式

- 公開ページはSSR/SSGでクローラブルにする(CSRのみはOGP/初期表示に不利)
- 重要コンテンツは初期HTMLに含める(JS依存を避ける)
- キャッシュ/CDN配信で高速化

### 第3章 メタ情報・OGP

| 項目 | 方針 |
| --- | --- |
| title/description | ページ固有・キーワードを反映、重複回避 |
| canonical | 正規URLを指定し重複を統合 |
| OGP/Twitter Card | タイトル/説明/画像でSNS表示最適化 |
| noindex | 非公開/重複/薄いページに付与 |

### 第4章 構造化データ(JSON-LD)

> ※ schema.orgのJSON-LDでリッチリザルトを狙う。

| ページ | スキーマ |
| --- | --- |
| トップ/会社 | Organization / WebSite |
| 料金/製品 | Product / Offer |
| ヘルプ/FAQ | FAQPage |
| ブログ記事 | Article / BreadcrumbList |

### 第5章 サイトマップ・robots

- sitemap.xmlを自動生成し検索エンジンへ送信
- robots.txtでクロール制御(アプリ配下はDisallow/noindex)
- 公開/非公開の切替を設計に組み込む(共有ページ)

### 第6章 URL設計・多言語

- URLは短く意味的に(例: /pricing, /blog/{slug})、変更時は301
- 多言語はhreflangで対応(国際化設計と連携)、canonicalと整合
- パラメータによる重複を避け正規化

### 第7章 パフォーマンス(Core Web Vitals)

> ※ Googleの評価指標。目標値を満たすよう設計・監視。

| 指標 | 内容 | 目標 |
| --- | --- | --- |
| LCP | 最大コンテンツ描画 | 2.5秒以内 |
| INP | 操作応答性(FIDの後継) | 200ms以内 |
| CLS | レイアウト安定性 | 0.1以下 |

- 画像最適化(遅延読込/次世代形式)、フォント/JS最適化、CDN

### 第8章 計測・改善

- Search Console/検索順位/流入を計測(計測設計と連携)
- CWVを継続監視し、劣化を検知して改善
- コンテンツSEOはキーワード設計→制作→効果測定のサイクル

### 第5章 応答・解決SLA

> ※ プラン/優先度により初回応答・解決目標を定義(未達時はクレジット等)。

| 優先度 | 初回応答 | 解決目標 | 対応時間 |
| --- | --- | --- | --- |
| 緊急(P1) | 30分以内 | 4時間目標 | 24/365 |
| 高(P2) | 2時間以内 | 1営業日 | 営業時間 |
| 中(P3) | 1営業日 | 3営業日 | 営業時間 |
| 低(P4) | 2営業日 | 計画対応 | 営業時間 |

### 第6章 エスカレーションマトリクス

> ※ 図『エスカレーションフロー』参照。障害は運用設計のSEVと連動。

| 条件 | エスカレーション先 | 期限/契機 |
| --- | --- | --- |
| L1で解決不可 | L2へ | 初回応答SLA内 |
| 再現/恒久対応が必要 | L3(開発/SRE)へ | 調査後速やかに |
| 重大障害(全断/漏えい) | インシデント(SEV1)＋経営 | 即時 |
| 課金/契約の重大 | 責任者＋経理 | 当日 |
| SLA逸脱のおそれ | マネージャ | 逸脱前に通知 |

### 第7章 インシデント連携

- 重大はサポート→インシデント管理(運用設計SEV/オンコール)へ引き継ぎ
- 顧客影響はステータスページ/告知で周知(BCPと連携)
- 時系列・対応・恒久策を記録しポストモーテムへ

### 第8章 ナレッジ・フィードバック

- よくある問い合わせをFAQ/ヘルプに反映し自己解決を促進
- 要望/不満はVOCとして課題管理(14)・プロダクトへ連携
- 問い合わせ件数/解決時間/CSATを計測し改善(計測設計と連携)

### TeamFlow / 用語集・データディクショナリ


### 第1章 目的・運用

- 用語の唯一の源(SSOT)として、要件・設計・BDD・コードで共通利用
- 表記ゆれを統一し、変更は変更管理を通す
- ドメイン用語はドメインモデル設計(ユビキタス言語)と同期

### 第2章 ビジネス/ドメイン用語

| 用語 | 定義 | 英語/i18nキー |
| --- | --- | --- |
| テナント | 契約・分離の境界となる組織 | tenant |
| プロジェクト | タスクを束ねる作業単位 | project |
| タスク | 担当・期限・状態を持つ作業項目 | task |
| サブスクリプション | テナントの課金契約 | subscription |
